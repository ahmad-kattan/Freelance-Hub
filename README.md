# FreelanceHub: Backend API

خادم (Backend) منصة **FreelanceHub**: منصة عمل حر تجمع أصحاب المشاريع (Clients) بالمستقلين (Freelancers)، وتحمي الطرفين بنظام **ضمان مالي (Escrow)**: عند قبول العرض يُحجز المبلغ داخل المنصة، ولا يصل للمستقل إلا بعد موافقة العميل على التسليم (أو بعد انتهاء مهلة المراجعة)، مع خصم غرامة عن أي تأخير في التسليم.

## الميزات

| الدور | ما يستطيع فعله |
|---|---|
| **العميل** (`CLIENT`) | ينشر مشاريع (مع مرفق اختياري)، يستقبل العروض ويقارنها، يقبل عرضاً (يُحجز المبلغ)، يراجع التسليم ويوافق أو يطلب تعديلاً، يشحن محفظته. وإن تأخر المستقل عن الموعد يسترد جزءاً من المبلغ تلقائياً |
| **المستقل** (`FREELANCER`) | ملف شخصي (صورة، نبذة، سعر بالساعة)، يتصفح المشاريع ويقدم عروضاً، يسلّم العمل، يستلم أرباحه (90% بعد خصم أي غرامة تأخير) في محفظته |
| **المدير** (`ADMIN`) | يدير التصنيفات، يحظر المستخدمين ويفك الحظر، محفظته هي محفظة المنصة (العمولة 10%) |

ومعها:

- **موافقة تلقائية:** إن سلّم المستقل ولم يرد العميل خلال مهلة محددة (يومان افتراضياً) توافق المنصة نيابة عنه ويُدفع للمستقل.
- **غرامة تأخير:** نسبة من السعر عن كل يوم تأخير في التسليم، بسقف أقصى، ترجع للعميل.
- تسجيل دخول من عدة أجهزة وإدارتها، حظر فوري، حدود لعدد الطلبات (Rate Limiting)، وتوثيق تفاعلي (Swagger).

## التقنيات

- **NestJS** (TypeScript)
- **PostgreSQL** + **Prisma** (ORM)
- **JWT** (Access + Refresh Tokens) و **bcrypt**
- **Multer** لرفع الملفات، و **file-type** للتحقق من النوع الحقيقي
- **@nestjs/throttler** (Rate Limiting)، و **@nestjs/cache-manager** (كاش التصنيفات)
- **@nestjs/schedule** (المهام المجدولة: الموافقة التلقائية)
- **Swagger** (`@nestjs/swagger`)

## التشغيل المحلي

**المتطلبات:** Node.js 20 أو أحدث، و PostgreSQL 14 أو أحدث.

```bash
# 1) تثبيت الحزم
npm install

# 2) إعداد البيئة: انسخ الملف وعدّل القيم (انظر الجدول أدناه)
cp .env.example .env

# 3) إنشاء الجداول (ويولّد Prisma Client تلقائياً)
npx prisma migrate dev

# 4) تعبئة البيانات (حساب المدير ومحفظته، التصنيفات، والبيانات التجريبية)
npx prisma db seed

# 5) تشغيل الخادم
npm run start:dev
```

بعد التشغيل:

- **التوثيق التفاعلي (Swagger):** <http://localhost:3000/docs>
- **ملف OpenAPI (JSON):** <http://localhost:3000/docs-json> (يمكن استيراده في Postman: Import ثم Link)

> إن غيّرت المنفذ في `main.ts` فغيّر الروابط أعلاه.

## نظرة على الـ API

التفاصيل الكاملة (الحقول، والأخطاء، والتجربة المباشرة) في **Swagger** على `/docs`. هذه خريطة سريعة:

| القسم | Endpoints الأساسية |
|---|---|
| **Auth** | `POST /auth/register` · `/auth/login` · `/auth/refresh` · `GET /auth/profile` · `GET /auth/sessions` · `POST /auth/logout` · `/auth/logout-others` · `/auth/logout-all` · `DELETE /auth/sessions/:id` |
| **Users** | `GET /users` (مدير) · `GET /users/:id` · `PATCH /users/me` · `PATCH /users/:id/ban` و `/unban` (مدير) |
| **Freelancers** | `GET /freelancers/:id` (عام) · `GET/PATCH /freelancers/me` · `PUT /freelancers/me/avatar` |
| **Categories** | `GET /categories` (عام، مكاش) · `POST` · `PATCH /:id` · `DELETE /:id` (مدير) |
| **Projects** | `POST /projects` · `GET /projects` (تصفح) · `GET /projects/mine` · `GET /projects/:id` · `PATCH` · `DELETE` · `GET /projects/:id/attachment` |
| **Proposals** | `POST /projects/:id/proposals` · `GET /projects/:id/proposals` · `GET /proposals/mine` · `POST /proposals/:id/accept` |
| **Wallet** | `GET /wallet/me` · `POST /wallet/deposit` · `GET /wallet/transactions` |
| **Delivery** | `PUT /projects/:id/delivery` · `GET .../delivery` · `GET .../delivery/file` · `POST .../delivery/request-revision` · `POST .../delivery/approve` |

### اتفاقيات الـ API (مهمة لفريق الواجهات)

- **الرد الناجح:** `{ "success": true, "data": ... }`. والقوائم تضيف `"meta": { total, page, limit, totalPages, hasNextPage, hasPreviousPage }`.
- **الخطأ:** `{ "success": false, "statusCode": 400, "message": "...", "errors": [...], "timestamp": "...", "path": "..." }`.
- **المعرّفات نصوص:** `"id": "12"` (نوع `BigInt`). وأرسلها نصوصاً أيضاً عندما تُرسَل في الجسم (مثل `categoryId`).
- **المبالغ بالسنت:** أعداد صحيحة. `50000` = $500.00. الطلبات ترسل أعداداً، والردود ترجع نصوصاً. العملة دولار فقط.
- **الحماية:** `Authorization: Bearer <access_token>`. الـ Access Token يعيش 15 دقيقة، ويجدَّد بـ `/auth/refresh`.
- **رفع الملفات:** `multipart/form-data`، وأسماء الحقول: `avatar` (2MB)، و`attachment` (5MB)، و`file` (10MB).
- **الحدود:** الدخول 5 محاولات في الدقيقة، وبقية الطلبات 100 في الدقيقة لكل IP. (HTTP 429 عند التجاوز.)

### حقول مهمة في الردود (للمواعيد والغرامة)

**المشروع** (`GET /projects/:id`):

- **`dueAt`**: الموعد النهائي (وقت قبول العرض + `durationDays`). `null` للمشروع `OPEN`.
- **`acceptedProposal`**: `{ id, price, durationDays, freelancerId }` عندما يكون للمشروع عرض مقبول (`IN_PROGRESS` أو `COMPLETED`)، و`null` عندما يكون `OPEN`. `price` بالسنت (نص)، وبه تحسب الواجهة الغرامة.

**القوائم:**

- `GET /projects/mine` و`GET /projects`: يضيفان `dueAt` و`delivery: { autoApproved } | null` لكل مشروع، لعرض "باقي 3 أيام" أو "متأخر" على البطاقة دون فتح المشروع.
- `GET /proposals/mine`: داخل `project` يوجد `dueAt` و`delivery: { autoApproved } | null`.

**التسليم** (`PUT` و`GET .../delivery` و`request-revision`):

| الحقل | المعنى |
|---|---|
| `autoApproved` | `true` إن كانت الموافقة تلقائية من النظام، و`false` إن وافق العميل بنفسه (أو لم تتم الموافقة بعد) |
| `firstSubmittedAt` | وقت **أول** رفع. لا يتغير عند إعادة الرفع بعد طلب التعديل، وعليه يُقاس التأخير |
| `submittedAt` | وقت **آخر** رفع. عليه تُحسب مهلة الموافقة التلقائية |
| `lateDays` | عدد أيام التأخير (`0` إن سُلّم في الموعد) |
| `latePenalty` | الغرامة بالسنت (نص، `"0"` إن لم يتأخر) |
| `reviewedAt` | وقت قرار المراجعة: طلب التعديل، أو الموافقة (اليدوية أو التلقائية). يعود `null` عند رفع نسخة جديدة |

- **قبل الموافقة** (`SUBMITTED` أو `REVISION_REQUESTED`): `lateDays` و`latePenalty` **معاينة** ("لو وافق العميل الآن") تُحسب من `dueAt` وأول تسليم وسعر العرض ونسب الغرامة الحالية.
- **بعد الموافقة** (`APPROVED`): القيمتان **نهائيتان ومخزّنتان** لحظة الموافقة، فتغيير نسب الغرامة بعدها لا يغيّرهما.

**رد `POST .../delivery/approve`** فيه، بالإضافة إلى `paidToFreelancer` و`platformCommission` و`total`: `lateDays` و`latePenalty` (نص).

## تدفق المال

مثال: العميلة سارة تقبل عرض أحمد بـ $200.

### بدون تأخير

| الحدث | رصيد سارة (متاح / محجوز) | أحمد | المنصة |
|---|---|---|---|
| شحن $300 (`DEPOSIT`) | 30000 / 0 | 0 | 0 |
| قبول العرض (`HOLD`) | 10000 / 20000 | 0 | 0 |
| موافقة سارة على التسليم (`RELEASE` + `EARNING` + `COMMISSION`) | 10000 / 0 | **18000** | **2000** |

### مع تأخير 3 أيام

الغرامة = 3 × 5% = **15%** من السعر = $30. وتُحسب العمولة على المبلغ **بعد** الخصم.

| الحدث | رصيد سارة (متاح / محجوز) | أحمد | المنصة |
|---|---|---|---|
| شحن $300 (`DEPOSIT`) | 30000 / 0 | 0 | 0 |
| قبول العرض (`HOLD`) | 10000 / 20000 | 0 | 0 |
| الموافقة (`RELEASE` + `PENALTY_REFUND` + `EARNING` + `COMMISSION`) | **13000** / 0 | **15300** | **1700** |

الحساب: الغرامة `3000` (ترجع لسارة)، والمبلغ بعد الخصم `17000`، العمولة `floor(17000 × 10 / 100) = 1700`، وأحمد `17000 − 1700 = 15300`.

**قاعدة ذهبية للتحقق:** لا يوجد مال يُخلق أو يختفي. مجموع كل الأرصدة (متاح + محجوز) يساوي دائماً مجموع كل الشحنات (وتبقى صحيحة مع الغرامة لأن الغرامة تنتقل بين محافظ ولا تُخلق):

```sql
SELECT
  (SELECT COALESCE(SUM("availableBalance" + "reservedBalance"), 0) FROM "Wallet") AS wallets_total,
  (SELECT COALESCE(SUM(amount), 0) FROM "WalletTransaction" WHERE type = 'DEPOSIT') AS deposits_total;
```

## القرارات التقنية وأسبابها

### المال
- **أعداد صحيحة بالسنت (`BigInt`) وليس `float`:** لتفادي أخطاء التقريب (مثل `0.1 + 0.2`). الدقة حتى آخر سنت.
- **العمولة:** `floor(المبلغ بعد الغرامة × 10 / 100)` والباقي للمستقل، فالمجموع دقيق دائماً ولا يضيع أي سنت. ($200 بدون تأخير ← عمولة 20 ومستقل 180.)
- **سجل حركات (Ledger) لا يُعدَّل ولا يُحذف:** كل حركة تسجّل الرصيدين بعدها للتدقيق. والفهرس الفريد `(projectId, walletId, type)` يمنع تكرار أي حركة لنفس المشروع، فالدفع المزدوج مستحيل على مستوى القاعدة.
- **محفظة المنصة:** هي محفظة حساب المدير الوحيد (من الـ Seed).

### العمليات الذرّية والتزامن
كل عملية مالية تعمل داخل **Transaction واحدة**، وأول خطوة فيها **تحويل شرطي لحالة المشروع** داخل `UPDATE` نفسه (Compare-and-Set). هذا ما يجعل الحالات التالية آمنة:

| الحالة | كيف نضمنها |
|---|---|
| قبول عرضين في نفس اللحظة | الأول يقفل صف المشروع، والثاني ينتظر ثم يجد الحالة تغيّرت فيفشل (409) قبل أن يلمس المحفظة |
| الضغط المزدوج على "موافقة" | نفس الآلية: الدفع مرة واحدة فقط |
| موافقة العميل في نفس لحظة الموافقة التلقائية (أو طلب تعديل) | نفس الآلية: واحد ينجح والآخر يفشل. والمهمة المجدولة تتجاهل الخسارة بصمت ولا تدفع مرتين |
| فشل أي خطوة (مثلاً رصيد غير كافٍ) | تراجع كامل (Rollback): لا حجز بلا عقد، ولا قبول بلا حجز |
| عرضان من نفس المستقل | قيد فريد `(projectId, freelancerId)` في القاعدة (وليس فحصاً في الكود فقط) |
| طلبا شحن/خصم متزامنان | تحديث ذرّي (`increment` / شرط `gte` داخل `UPDATE`) فلا يضيع تحديث ولا يصبح الرصيد سالباً |
| أقفال متعاكسة (Deadlock) | ترتيب ثابت: المشروع أولاً ثم المحافظ مرتبة حسب `id` |

### الموافقة التلقائية والمهام المجدولة
- **مهمة cron** (`@nestjs/schedule`) تعمل **كل ساعة**، وتبحث عن تسليمات حالتها `SUBMITTED` مرّ على رفعها أكثر من `AUTO_APPROVE_DAYS`، فتوافق عليها بنفس منطق موافقة العميل.
- **منطق واحد للموافقتين:** الموافقة اليدوية والتلقائية تمران عبر الدالة الداخلية نفسها (`settleApproval`)، فلا يتكرر الكود المالي، وتُطبَّق الغرامة بالطريقة نفسها في الحالتين.
- **كل مشروع بـ Transaction مستقلة:** فشل مشروع واحد لا يوقف الباقي، وتُعالَج دفعة بحد أقصى 100 مشروع في كل تشغيلة.
- **تشغيلتان متداخلتان:** حارس داخل النسخة يمنع تداخلهما، وعلى مستوى القاعدة يحمينا الـ Compare-and-Set والفهرس الفريد من الدفع المزدوج حتى لو اشتغلت المهمة على أكثر من نسخة.
- **التمييز:** حقل `autoApproved` في التسليم يبيّن أن الموافقة جاءت من النظام وليست من العميل.

### غرامة التأخير
- **الموعد النهائي (`dueAt`):** يُحسب عند قبول العرض: `وقت القبول + durationDays` من العرض المقبول.
- **القياس من أول تسليم:** عدد أيام التأخير = الفرق بين `dueAt` ووقت **أول** رفع (`firstSubmittedAt`) مقرَّباً لأعلى (أي جزء من اليوم يُحسب يوماً كاملاً). وبهذا لا يتحمل المستقل تأخر العميل في الرد، ولا يتأثر بإعادة الرفع بعد طلب التعديل.
- **الحساب:** `الغرامة = floor(السعر × min(أيام التأخير × النسبة اليومية، السقف) / 100)`. القيم الافتراضية: 5% يومياً وسقف 30% (قابلة للتغيير من متغيرات البيئة).
- **الغرامة ترجع للعميل** بحركة `PENALTY_REFUND`، وليست دخلاً للمنصة. ولهذا تبقى القاعدة الذهبية صحيحة.
- **السقف:** حتى لا يفقد المستقل كل دافع للتسليم المتأخر بدل ألا يسلّم أبداً.
- **تخزين النتيجة عند الموافقة:** تُحفظ `lateDays` و`latePenalty` في التسليم داخل نفس الـ Transaction التي تدفع، فتبقى القيمة النهائية ثابتة لو غُيّرت نسب الغرامة لاحقاً من متغيرات البيئة. وقبل الموافقة تُحسب معاينة حيّة من القيم الحالية.
- **المشاريع والتسليمات قبل هذه الميزة:** `dueAt = null` فلا غرامة، وقيم `lateDays` و`latePenalty` الافتراضية `0`.

### الأمان
- **كلمات المرور:** مُجزَّأة بـ bcrypt (لا تُقرأ حتى من قاعدة البيانات).
- **الجلسات:** Access Token قصير (15 دقيقة) + Refresh Token (7 أيام) **يُدوَّر عند كل تجديد**. استخدام Refresh Token قديم يعني احتمال سرقته، فتُلغى **كل** جلسات المستخدم فوراً. والتوكنات مخزنة مُجزَّأة (SHA-256).
- **الأجهزة:** كل جلسة تسجّل نوع الجهاز وعنوان IP ووقت الدخول، ويمكن إنهاء جهاز معيّن أو كل الأجهزة.
- **الحظر الفوري:** الـ `JwtStrategy` يفحص حالة المستخدم والجلسة **في كل طلب**، فيتوقف المحظور فوراً حتى لو كان توكنه ما زال صالحاً.
- **ثلاث طبقات للصلاحيات:** (1) التوكن، (2) الدور (`@Auth(UserRole.X)`)، (3) **الملكية** (هذا مشروعك؟ هذه محفظتك؟). وأغلب المسارات لا تستقبل معرّف المستخدم أصلاً بل تأخذه من التوكن، فلا يمكن الوصول لبيانات غيرك بتغيير رقم في الرابط.
- **404 بدل 403 للمخفي:** من لا يحق له رؤية مشروع أو تسليم يحصل على 404، فلا نكشف وجوده.
- **التحقق من المدخلات:** `ValidationPipe` مع `whitelist` و`forbidNonWhitelisted`، فلا يستطيع أحد إرسال حقل غير مسموح (مثل `role` أو `status` أو `isBanned`) أو تعديل حالة بنفسه.

### الملفات
- **النوع الحقيقي (Magic Bytes) وليس الامتداد أو الـ header:** ملف `fake.png` وهو نص عادي يُرفض.
- **أسماء عشوائية (UUID)** بامتداد نحدده نحن، فلا تضارب ولا Path Traversal.
- **عام وخاص:** الصور الشخصية فقط تُقدَّم مباشرة. مرفقات المشاريع وملفات التسليم **خاصة**: تُفتح عبر endpoint يفحص الصلاحية، مع `X-Content-Type-Options: nosniff`.
- **تنظيف:** فشل الحفظ في القاعدة يحذف الملف الجديد، واستبدال ملف يحذف القديم.

### الأداء
- **التصفح:** Pagination دائماً (مع `total` و`totalPages`)، وفهارس على `(status, categoryId, createdAt)` و`(status, budget)`، وترتيب ثانوي بالـ `id` لثبات الصفحات.
- **التصنيفات:** كاش في الذاكرة (10 دقائق) **يُمسح فوراً** عند أي تعديل من المدير.
- **ملف المستقل:** استعلام واحد بحقول محددة (لا N+1).

### أخرى
- **حذف ناعم** للمشاريع (`deletedAt`): تختفي من المنصة وتبقى في القاعدة للرجوع إليها.
- **ردود وأخطاء موحدة الشكل** عبر `ResponseInterceptor` و`AllExceptionsFilter`.
- **لا قيود `CHECK` في القاعدة:** تُطبَّق قواعد المدخلات في الـ DTOs، وحماية الرصيد بتحديث شرطي داخل `UPDATE` (أي كود يعدّل الرصيد يلتزم بهذا النمط).

## قرارات الأعمال (النقاط غير الواضحة)

الوصف الأصلي ترك بعض الحالات مفتوحة، وهذه القرارات المتخذة:

| الموضوع | القرار | السبب |
|---|---|---|
| جدول عقد منفصل | **لا**. المشروع يحمل `acceptedProposalId` (فريد) | لا مراحل ولا عقود متعددة في هذه النسخة، فجدول أقل وأبسط وفيه الضمان نفسه |
| سحب المستقل لأرباحه | **غير موجود**، تبقى في المحفظة | النص لا يذكره، ولا توجد بوابة دفع |
| تعديل العرض أو سحبه | **غير مسموح** | غير مذكور؛ والحالات تبقى ثلاثاً: `PENDING` و`ACCEPTED` و`REJECTED` |
| سعر العرض مقابل ميزانية المشروع | **غير مقيَّد** | قد يعرض المستقل أقل أو أكثر؛ القرار للعميل |
| عمولة المنصة | `floor(المبلغ بعد الغرامة × 10%)` | لا يضيع أي سنت، والمستقل يُحاسَب على ما استلمه فعلاً |
| عرض واحد لكل مستقل | قيد فريد في القاعدة | يصمد أمام الضغط المزدوج |
| تعديل/حذف المشروع | فقط وهو `OPEN` ومن صاحبه، والحذف ناعم | كما في النص |
| التسليم | تسليم واحد لكل مشروع، ملفه PDF أو مضغوط (zip/rar/7z) حتى 10MB، خاص بالطرفين | النص |
| رفض العميل للتسليم | **طلب تعديل بملاحظة**، فيرفع المستقل ملفاً جديداً | حتى لا يكون أمام العميل قرار القبول فقط |
| الملف أثناء المراجعة | **مجمَّد** حتى يقرر العميل | يضمن أن العميل يوافق على الملف الذي راجعه فعلاً |
| عميل لا يرد على التسليم | **موافقة تلقائية** بعد `AUTO_APPROVE_DAYS` (افتراضياً يومان) من آخر رفع | لا يبقى مال المستقل محجوزاً بسبب تجاهل العميل |
| ماذا يبدأ منه العدّاد | **آخر رفع** (`submittedAt`). كل نسخة جديدة بعد التعديل تبدأ المهلة من جديد | يعطي العميل وقتاً كاملاً لمراجعة كل نسخة |
| الموافقة التلقائية أثناء طلب التعديل | **لا تنطبق** (فقط على `SUBMITTED`) | المستقل هو من يجب أن يتحرك بهذه الحالة |
| تأخر المستقل عن الموعد | **غرامة** 5% من السعر عن كل يوم، بسقف 30%، ترجع للعميل | تحفّز الالتزام بالمواعيد دون أن يفقد المستقل كل شيء |
| ما هو "التأخير" | وقت **أول** تسليم بعد `dueAt` (القبول + مدة العرض)، وأي جزء من اليوم يُحسب يوماً | لا يتحمل المستقل تأخر العميل أو وقت التعديلات |
| العمولة مع الغرامة | تُحسب على المبلغ **بعد** الغرامة | المنصة تأخذ نسبتها مما حُوِّل فعلاً |
| معاينة الغرامة | تظهر للطرفين في رد التسليم قبل الموافقة | يعرف العميل والمستقل ما سيحدث قبل القرار |
| المشاريع القائمة قبل الميزة | `dueAt = null` فلا غرامة عليها | لا نفرض غرامة بأثر رجعي |
| حظر مستخدم عنده مشروع `IN_PROGRESS` | **مرفوض (409)**، سواء كان العميل أو المستقل المقبول | لا يوجد مشروع عالق ولا مال محجوز لا يصل لأحد |
| المدير | حساب واحد من الـ Seed؛ لا يُحظر ولا يُنشأ من التسجيل | محفظته هي محفظة المنصة |
| مشروع غير مفتوح | لا يظهر في التصفح ولا يقبل عروضاً | كما في النص |
| الأوقات | تُخزَّن UTC | تتحول في الواجهة لمنطقة المستخدم |

## حدود النسخة الحالية

هذه أمور خارج نطاق النص الحالي، وهي مرشحة للتطوير:

- **بوابة دفع حقيقية:** الشحن الحالي يضيف المبلغ مباشرة (كما طلب النص).
- **سحب الأرباح** من المحفظة إلى الخارج.
- **النزاعات:** العميل يستطيع طلب تعديل بلا حد أقصى، ولا يوجد تحكيم من المدير. المقترح: حد أقصى لعدد التعديلات، أو endpoint يقرر فيه المدير (رد المبلغ أو الدفع).
- **مشروع لا يُسلَّم أبداً:** الغرامة تتوقف عند السقف (30%) ولا يوجد إلغاء تلقائي للمشروع ولا رد كامل للمبلغ. يحتاج لقرار منفصل (إلغاء `CANCELLED` ورد المبلغ).
- **الإشعارات والبريد الإلكتروني:** بما فيها تنبيه العميل قبل الموافقة التلقائية، وإخبار المستقل بالموافقة أو بالغرامة.
- **أكثر من نسخة من الخادم:** الكاش وعدّاد الـ Rate Limit داخل الذاكرة (لكل نسخة)، والمهمة المجدولة تعمل على كل نسخة (والدفع المزدوج ممنوع بالقاعدة). عند التوسع ننقل الكاش والعدّاد إلى Redis، ونحصر المهمة بنسخة واحدة.
- **البحث:** يستخدم `ILIKE` على العنوان. مع عشرات الآلاف من المشاريع يُنصح بفهرس `pg_trgm` (Migration يدوي).
- **تنظيف دوري** لجدول `RefreshToken` (الصفوف المستخدمة والمنتهية).
- **فحص الفيروسات** للملفات المرفوعة (نتحقق من النوع فقط).
- **تقييمات المستقلين ومهاراتهم** (غير موجودة في الوصف المختصر).

## سيناريو تجربة كامل

يمكن تنفيذه كله من صفحة **Swagger** (`/docs`). لكل مستخدم سجّل الدخول من `POST /auth/login`، ثم اضغط **Authorize** وألصق الـ `access_token` (بدون كلمة Bearer). والتوكن ينتهي بعد 15 دقيقة.

1. **المدير:** تأكد أن `GET /categories` يعرض التصنيفات.
2. **سارة (CLIENT):** `POST /wallet/deposit` بـ `{ "amount": 30000 }`، ثم `POST /projects` (مشروع "تصميم شعار" بميزانية `20000`).
3. **أحمد وليلى (FREELANCER):** كلاهما `GET /projects` ثم `POST /projects/{id}/proposals` (أحمد بـ `20000`، وليلى بـ `25000`).
4. **سارة:** `GET /projects/{id}/proposals` لمقارنة العروض، ثم `POST /proposals/{id}/accept` على عرض أحمد.
   - `GET /wallet/me`: متاح `10000` ومحجوز `20000`. المشروع `IN_PROGRESS`، وعرض ليلى `REJECTED`.
5. **أحمد:** `PUT /projects/{id}/delivery` (ملف PDF).
6. **سارة:** `POST /projects/{id}/delivery/request-revision` بملاحظة، ثم **أحمد** يرفع ملفاً جديداً.
7. **سارة:** `POST /projects/{id}/delivery/approve`.
   - الرد: `paidToFreelancer: "18000"` و`platformCommission: "2000"` و`lateDays: 0` و`latePenalty: "0"`.
   - المشروع `COMPLETED`، ومحجوز سارة `0`.
8. **أحمد:** `GET /wallet/me` ثم `GET /wallet/transactions` يرى `EARNING` بـ 18000.
9. **المدير:** `GET /wallet/me` يرى رصيد المنصة 2000، وحركة `COMMISSION`.

للتحقق من الأمان جرّب أيضاً: ضغط "موافقة" مرتين (الثانية 409)، وتقديم عرضين من المستقل نفسه (الثاني 409)، وحظر مستخدم عنده مشروع جارٍ (409)، وفتح مشروع غيرك برقمه (404).

### تجربة غرامة التأخير

الموعد النهائي يتحدد عند قبول العرض، فلتجربة التأخير دون الانتظار عدّله يدوياً **قبل** أن يسلّم المستقل:

```sql
UPDATE "Project" SET "dueAt" = now() - interval '3 days' WHERE id = <معرّف المشروع>;
```

ثم كرّر الخطوات 5 و7 أعلاه (مع مشروع جديد قُبل عرضه). النتيجة المتوقعة لمشروع بـ `20000`:

- قبل الموافقة: `GET /projects/{id}/delivery` يعرض المعاينة (`lateDays: 3` و`latePenalty: "3000"`).
- رد `approve`: `lateDays: 3` و`latePenalty: "3000"` و`paidToFreelancer: "15300"` و`platformCommission: "1700"`.
- بعد الموافقة: `GET .../delivery` يعرض `status: APPROVED` و`autoApproved: false` و`reviewedAt` بوقت الموافقة، والغرامة نفسها (مخزّنة).
- `GET /projects/{id}` يعرض `dueAt` و`acceptedProposal` بالسعر، و`GET /projects/mine` و`GET /proposals/mine` يعرضان `dueAt` و`delivery.autoApproved`.
- سارة: `GET /wallet/transactions` يظهر فيه `RELEASE` و`PENALTY_REFUND` (3000)، ورصيدها المتاح يزيد 3000.
- جرّب أيضاً مسار التعديل: سلّم متأخراً، اطلب تعديلاً، سلّم مرة ثانية، ثم وافق. يبقى `lateDays` محسوباً من **أول** تسليم.
- شغّل **القاعدة الذهبية** (الاستعلام في قسم تدفق المال) وتأكد أن الرقمين متساويان.

### تجربة الموافقة التلقائية

لتجربتها دون الانتظار يومين:

1. بدّل مؤقتاً `CronExpression.EVERY_HOUR` إلى `CronExpression.EVERY_10_SECONDS` في `delivery.scheduler.ts`.
2. جهّز مشروعاً فيه تسليم بحالة `SUBMITTED`، ثم قدّم تاريخ رفعه:
   ```sql
   UPDATE "Delivery" SET "submittedAt" = now() - interval '3 days' WHERE "projectId" = <معرّف المشروع>;
   ```
3. خلال 10 ثوان يصير المشروع `COMPLETED` والتسليم `APPROVED` مع `autoApproved = true` و`reviewedAt` بوقت الموافقة، وتنزل الأرباح في محفظة المستقل.
4. تأكد أن تسليماً بحالة `REVISION_REQUESTED` (حتى لو قدّمت تاريخه) **لا** يتأثر.
5. أعد الـ cron إلى `EVERY_HOUR`.
